# Architectural acceptability rubric

Written before the next rule changes, 15 November 2026. These are project-specific engineering expectations authored with disclosed AI assistance, not organiser answer keys or independent expert labels. They test architectural behavior rather than scenario IDs in the engine. Many alternative products can be defensible.

| Brief | Acceptable proposals | Known-bad behavior | Reason |
|---|---|---|---|
| P1: Markdown portfolio | Static HTML/Astro-style output; no backend/database; bounded static hosting | Dynamic database, identity cluster or Kubernetes with no requested feature | Publishing is a content build, and the budget is zero. |
| P2: service marketplace | Web/Android clients; known JS/Python backend; transactional searchable data; actual phone delivery, checkout, shared chat, storage and retryable workers | Missing OTP/payment/search; SQLite on ephemeral replicas; invented India compliance; an over-budget plan selected while a compatible upper-bound budget fit exists | Features need complete integrations. Bundle allowances and fees must be counted once. |
| P3: collaborative whiteboard | TypeScript/Go-capable backend (Fastify, NestJS/Express with reviewed services, or Go); persistent collaborative state, isolation and workers; explicit latency test task | Claiming any framework meets 100 ms without measurement; omitting Go from viable candidate review; independent per-instance in-memory state | Team familiarity is real evidence; framework latency superiority is not established. A tied Fastify/Go pair is acceptable. |
| P4: Java/Kotlin/TypeScript senior fintech team | JVM/Spring ecosystem preferred when compatible and affordable; relational ledger and separately scoped inference/payment/KYC integration | Selecting an equally affordable generic JS backend while discarding the team's explicitly supported JVM languages; treating checkout as a complete lending system | Existing server ecosystem depth should influence delivery and maintenance, without adding security or performance credit. |
| P5: C#/SQL team with existing on-premises SQL Server 2019 | ASP.NET-compatible integration with existing SQL Server; retain Entra; explicit private connectivity, geography, license and capacity qualifications | Automatically migrating to PostgreSQL, inventing the on-premises server's country or free licensing, or adding an unnecessary identity broker | Reuse must be technically eligible before a reuse preference can act. An existing server is not a newly purchased managed database. |
| P6: offline field survey | Native client persistence and durable sync/outbox; known Python/JS backend; real phone delivery; managed low-cost option when compatible | Online-only storage, treating a WebSocket as offline durability, omitting device-memory tests, or choosing an avoidably over-budget primary | Offline data and retry/conflict semantics are architectural requirements. |

The cross-case rules are: reject actual deployment/driver conflicts; preserve feature flags and critical qualifications; prefer an upper-bound infrastructure budget fit within the supported backend-language tier when one exists; use ecosystem familiarity and explicit system reuse as delivery/maintenance evidence; keep measured latency separate from implementation preference. Existing on-premises geography/capacity/license evidence remains unverified unless supplied and reviewed. Catalog and plan variants must make those assumptions visible.
