# Final report authoring outline

This is a working outline, not the final submission PDF. Replace placeholders with verified evidence. Do not submit this outline as a completed report.

Title page: challenge, full name, college, Unstop registered email, GitHub URL if any, date.

## 1. Abstract

≤150 words: implemented engine, chosen approach, coverage, actual results. Avoid unmeasured claims.

## 2. Problem understanding

Explain constraints, scope, optional defaults, distinctions between implementation technologies and recommended technologies. Discuss documented ambiguities.

## 3. System architecture

Actual diagram/modules/input-to-output data flow; technologies and exact versions; local deployment. Adapt TRD to match implementation.

## 4. Input design and research

Every mandatory/optional/extra input: architectural relevance, affected decisions, validation/default, evidence source. Show an example where each extra field changes a recommendation.

## 5. Knowledge base and decision logic

Actual catalog model, sources, filters, scoring, compatibility, tie-breaks, conflicts, determinism, cost assumptions. LLM usage declaration and disabling behavior. Include rule examples and limitations.

## 6. Sample recommendations

Real screenshots for P1–P6. Discuss at least two in depth: supplied constraints → chosen components → drivers → alternative rejections → trade-offs → costs/warnings. Include engine/catalog versions. No mockups presented as screenshots.

## 7. Edge-case handling

Table for missing fields, invalid values, contradictions, over-engineering, regulation, existing systems, restricted deployment, skill mismatch, deprecated technology. For each: detection, response, genuine screenshot.

## 8. Validation

Actual tests and changed-input checks; source-backed comparison with case studies or expert feedback if performed. Record machine, timing, setup and limitations. Never claim review or tests that did not happen.

## 9. Limitations and future work

Research gaps, unverified regional details, uncertain capacity/costs, catalog breadth, conflict handling limits, planned improvements.

## 10. References and third-party tools

All libraries, datasets, APIs, official docs/pricing, case studies, borrowed assets and scaffolds. Use exact linked sources and relevant dates. Map catalog source IDs to report references.

## 11. AI assistance declaration

Adapt AI_ASSISTANCE honestly: tools/models known, tasks, what owner reviewed, distinction between coding assistance and runtime LLM selection.

## Format/evidence limits

Sections 1–10 must fit within 15 A4 pages with 10–12 pt body. Optional appendices ≤10 pages. Aim to include section 11 within main limit where possible because its pagination is not explicit. Keep actual images legible; remove repetitive planning content. Render and visually review the final PDF before delivery.
